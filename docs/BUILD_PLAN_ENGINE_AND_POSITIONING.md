# Build Plan — from "thin engine" to "credible standalone reserving workbench"

*Turns the gaps and framing problems in `ACTUARY_REVIEW.md` into a sequenced plan. The strategic
spine, in one line:*

> **This must stand on its own.** A team with no reserving package should be able to run a real
> close in it. If they *also* own ResQ/Reserve Pro, they plug it in and get its craft — but not
> owning one is not a blocker. This is to reserving what pricing-workbench is to Radar:
> **"integrate it if you want to pay for it and get its benefits; if you don't, you get by with this."**

Three workstreams, run loosely in parallel but sequenced within each:

- **A · The engine** — close the actuarial gaps so a real actuary can book a cohort. (§2)
- **B · Positioning & framing** — fix the misleading bits; make the ResQ-optional stance explicit and honest. (§3)
- **C · MLflow & automation** — where model-management and scheduled runs genuinely earn their place. (§4)
- **D · Designer / Excel surface** — the low-code and spreadsheet on-ramps. (§5)

Each item carries a size (◔ hours · ◑ 1–2 days · ● 3–5 days), the actuary-review gap it closes,
and — non-negotiable per the project rules — how it **runs for real on Databricks** and stays
**gen2-clean** (spec-first, no business-data duplication, governed).

---

## 1 · Guardrails that apply to every item

Before the work: these are the standing constraints, so I don't restate them each time.

- **Spec-first.** Any new table/view/function is authored in `model/**.yaml` (gen2 ontology
  format), generated by `tools/generate.py`, deployed by `tools/deploy_databricks.py`. No hand-DDL.
- **No business-level duplication.** New triangles (incurred, net, counts) are **views** over the
  claim ledger, not stored parallel copies — same rule that made the paid triangle honest.
- **Runs for real.** Every method is an MLflow model in UC; every batch step is a real Job task;
  the app reads live tables. Nothing faked.
- **Every page keeps** its "what am I seeing" explainer + demo disclaimer, and asset labelling
  (`[reserving-workbench]`, `bxc_*` tags), enforced by the smoke test — which grows with each item.
- **Two personas, one asset.** Reserving books the number; pricing develops to ultimate for the
  indication. Every engine feature must serve both, and the UI must not tell a pricing actuary
  it's a reserving tool (the §3 framing fix).

## 2 · Workstream A — close the engine gaps

Ordered so the ★★★ "every-quarter" gaps come first. The goal is not ResQ parity; it's **enough
real actuarial method that a standalone team can defend a booked number.**

### A1 · Prior pattern as a factor row + "Hold prior" button ◔  *(closes: §4 top miss)*
The actuary compares *factor to factor*. Add a third read-only row in the decision grid — **prior
selection (SEL-…-PRIOR)** between empirical and selected — and a **Hold prior** button that copies
prior→selected in one click (pre-filling a rationale, not bypassing it). Fix `prior_reserve()` to
select the genuine prior (`SEL-2026Q3-PROP-PRIOR`), not this quarter's elected row. Pass real
`prior_factors` to the AI reviewer so it can do the one comparison that matters.
*Real/gen2:* no new data; UI + one query fix. **Do first — it's hours and it's the core screen.**

### A2 · Fitted, smoothed tail ◑  *(closes: "tail is one input box" ★★★)*
Replace the single tail box with a **tail-fit panel**: fit exponential / inverse-power / Weibull to
the last N selected factors, show the fitted curve beyond the observed triangle, let the actuary
accept the fitted tail or override. Store the chosen tail method + parameters on
`selected_development_pattern` (new columns: `tail_method_code`, `tail_params`, `tail_fitted_factors`).
*Real/gen2:* the fit is a UC Python function `fn_fit_tail(lob, method, n)` returning the curve;
spec'd as a function, deployed like `fn_empirical_ldf`. New `tail_method` code set.

### A3 · Method blending per cohort ●  *(closes: "can't blend methods" ★★★)*
This is what "selection" actually means beyond one factor. Add a **blend control** on Methods &
estimates: per accident year, weight CL vs BF (and a maturity rule — "CL beyond development N, BF
before"), plus **Benktander** and **Cape Cod** as first-class methods (Cape Cod derives the ELR
from the triangle; the review flagged both as missing). The blended ultimate writes to
`reserve_estimate` with `method='BLENDED'` and a `blend_spec` JSON recording the weights — so the
booked number's method mix is auditable.
*Real/gen2:* Benktander + Cape Cod join the method library as registered MLflow models (workstream
C); the blend is a governed function `fn_blend_estimate`. New `reserving_method` codes.

### A4 · Editable BF/ELR a-priori per cohort ◑  *(closes: "priors are fixed" ★★)*
The BF/ELR/Cape Cod a-priori loss ratio must be **user-set per accident year** in the UI, not baked
in. This is also the natural join to premium (already ingested from the pricing schema) — a-priori =
planning LR × earned premium. Write the chosen priors to a new `reserve_apriori` table so the
assumption is recorded, versioned, and reproducible.
*Real/gen2:* `reserve_apriori` entity (spec'd); premium already available via `1_raw_policy`.

### A5 · Gross-to-net (reinsurance) ●  *(closes: "no net" ★★★ dealbreaker-as-engine)*
Every reserve is booked gross *and* net. Even one flat layer makes "net ultimate" real. Add a
minimal **RI programme** table (quota-share % + one excess-of-loss layer: attachment, limit), a
**ceded triangle as a view**, and a net-of-RI column on estimates and on the committee view. Label
clearly as a modelled simplification.
*Real/gen2:* `reinsurance_programme` entity + `ceded_loss_development` view (derived, not stored);
`reserve_estimate` gains `ultimate_net`, `ibnr_net`. This is the single loudest silence for a
reserving actuary — worth the ● even if the RI model is deliberately simple.

### A6 · Bootstrap / full predictive distribution ●  *(closes: "Mack CoV only" ★★)*
Add **ODP bootstrap** (the actuary's real distribution, not just Mack's analytic CoV) as a method
producing a full simulated distribution → percentiles, a histogram, and the numbers the capital
team asks for. This is a strong MLflow story (C2): the bootstrap is a registered model, the
simulation is a scheduled Job, results land in a `reserve_distribution` table.
*Real/gen2:* runs as a real Job task (thousands of sims — not app-synchronous); `reserve_distribution`
entity. Ties workstream A to C.

### A7 · Incurred triangle + paid/incurred consistency ◑  *(closes: "paid-centric" ★★)*
The data already has incurred. Make the selection gesture **basis-aware** (paid | incurred), and add
a **paid-vs-incurred diagnostic** (are they converging? is the paid pattern lagging case?). Half of
real reserving is the incurred triangle and this consistency check.
*Real/gen2:* incurred triangle is already a column in `loss_development`; UI + a diagnostic view.

### A8 · Count & average-cost triangles (frequency-severity) ◑  *(closes: ★★ reserving, ★★★ pricing)*
Claim **counts**, **closure rates**, and **average cost** triangles — the frequency-severity view
pricing actuaries specifically need, and a cross-check reserving actuaries use. The review noted
this is "the same window functions over a count instead of an amount".
*Real/gen2:* count triangles are new views over the claim ledger (`COUNT` not `SUM`); no new raw data.

### A9 · Discounting + cohort basis ◑  *(closes: "no PV", "accident year only" ★★)*
(a) **Discount to present value** on a supplied yield curve → discounted best estimate (SII, IFRS 17
LIC). (b) Let the triangle be built on **underwriting or report year**, not only accident year.
*Real/gen2:* discount is a governed function over the cashflow pattern (already exists as
`reserve_cashflow_pattern`); cohort basis is a parameter on the triangle view.

### A10 · Cell-level actual-vs-expected heatmap ◔  *(closes: ★ residual diagnostic)*
Extend diagnostics from cohort-level first-step to a **residual heatmap across the whole triangle** —
the standard back-testing picture. Cheap, and it makes the Diagnostics page look like an actuary's.
*Real/gen2:* view over `actual_vs_expected` widened to all cells.

**Sequencing within A:** A1 (hours, do now) → A2, A5, A3 (the three ★★★) → A4, A6, A7 → A8, A9, A10.
After A1–A5 the honest claim changes from *"competent chain-ladder demo"* to *"a standalone team
could book a cohort in this"* — which is the whole objective.

## 3 · Workstream B — positioning & framing (the ResQ-optional stance)

The engine work is wasted if the demo still talks like a thin reserving tool or overclaims. This
workstream is mostly words and one new page — cheap, high-leverage, and it's where the
"pricing-workbench-to-Radar" positioning gets made explicit.

### B1 · Fix the misleading language ◔  *(closes: §4 framing tells)*
- "reserves recompute live" → "**ultimates recompute**" on the pricing path.
- "Selected IBNR" → "Selected ultimate / IBNR (unpaid)".
- Currency: relabel as **GBP (illustrative)** rather than a fake `$`, said once. (Convert to USD
  only if we commit to it end-to-end — doc, app, notebooks — not piecemeal.)
- The AI peer-review button: either wire it to the prior (done via A1) or hide it. With A1 it works,
  so **keep it and let it do the prior-vs-empirical challenge** — that's a good beat.

### B2 · The "Engines & your models" page becomes the positioning centrepiece ◑  *(the Radar-analogue)*
Rebuild it to mirror pricing-workbench's `RatingEngineIntegration` page, but inverted for the
standalone-first stance. Three clearly-labelled tracks:
1. **Standalone (default).** Everything here runs natively — CL, BF, Cape Cod, Benktander, bootstrap,
   tail-fit, net, discounting. *You do not need a reserving package to close.* This is the headline.
2. **Bring your own engine (R/Python).** Your model registered as a first-class method (already
   built) — your craft, our governance.
3. **Plug in a commercial package (optional).** If you own ResQ/Reserve Pro, the selection step is a
   seam: we prep the governed triangle, it makes the pick, we read it back into the same audited
   table (`source = RESQ`). *You pay for it and get its depth; you don't, you use track 1.*

The line, said explicitly, mirroring pricing/Radar:
> *"Integrate a reserving package if you want to pay for it and get its benefits — but if you don't,
> you get by with this. Either way the data, governance, and narrative live here."*

*Real/gen2:* the seam already exists in the schema (`source_code` enum). This is a page rebuild +
one honest SVG per track, no new data.

### B3 · A "what this does / doesn't do" honesty panel ◔  *(closes: ResQ-user trust)*
A short, in-app capability matrix: what runs natively (green), what you bring your own model for
(blue), what a commercial package still does better (grey — e.g. exotic curve families, decades of
edge cases). Being explicit about the boundary is what keeps a real actuary's trust — the review
was blunt that overclaiming loses the room.

### B4 · Update the demo docs + actuary-facing framing ◔
Fold the standalone-first stance into `DEMO_GUIDE.md` and the Aug docs: the workbench is a complete
reserving platform on its own, with a pluggable engine seam — not a wrapper that *needs* ResQ.

## 4 · Workstream C — MLflow model management & automation (where it earns its place)

You asked specifically: where does MLflow-controlled, automated model running genuinely add value?
Here's where it's real rather than decoration — every one is something a standalone team actually
benefits from.

### C1 · Every method is a registered, versioned, aliased UC model — extended ◑  *(build on notebook 04)*
Already true for the six methods. Extend to the new ones (Cape Cod, Benktander, ODP bootstrap,
tail-fit) so the **whole engine is MLflow-governed**: each method has a version history, a
`production`/`candidate` alias, a signature, and lineage. The value for a standalone team: **model
risk management for free** — "which version of chain-ladder booked Q2, and what changed since?" is a
query, not an investigation. This is the SR11-7 / TS 20-1 model-governance story regulators ask for.

### C2 · Scheduled quarterly reserving run as a Job ●  *(the automation you flagged)*
A parameterised **Databricks Job** that runs the whole close on a schedule or a trigger:
`source_sync → prep → build all triangles (paid/incurred/counts/net) → run every registered method →
bootstrap distribution → actual-vs-expected → write estimates`. This is where automation earns it:
- **Reproducible quarterly close** — the same governed run every quarter, versioned, with an MLflow
  run per method per cohort so every number traces to a model version + input snapshot.
- **The bootstrap (A6) *has* to be a Job** — thousands of sims aren't app-synchronous.
- **The guard stays** — the automated run still stops before an unapproved pattern reaches output.
*Real/gen2:* extends the existing `ldf_pipeline` Job; new task per method; MLflow autologging on.

### C3 · Champion/challenger + back-testing automation ◑  *(model monitoring, the real MLflow win)*
A scheduled job that **re-runs last year's selections against what actually emerged** (hindsight
testing) and logs the error per method to MLflow — so "which method has been most accurate on this
line over the last eight quarters?" is a tracked metric, not a memory. This is the genuinely
valuable, genuinely-MLflow capability a spreadsheet team can never build: **continuous method
validation**. Results → a `method_performance` table + an MLflow experiment view.
*Real/gen2:* new scheduled Job + `method_backtest` entity; reads existing history.

### C4 · Model approval gate as an MLflow alias transition ◔  *(ties governance to MLflow)*
Promoting a method to `production` (the alias) becomes the governed act — logged, attributed,
reversible, and the app shows the alias history. Rolling back a method is an alias flip, not a code
edit. Small, and it makes the "version-controlled and registered" claim fully real.

**Why this matters for the standalone stance:** a team without ResQ that adopts this gets *model
governance a spreadsheet team has never had* — versioning, back-testing, champion/challenger,
scheduled reproducible runs. That's not "ResQ-lite", it's a category (MLOps for reserving) the
incumbents largely don't offer. **This is a real differentiator, not a consolation prize.**

## 5 · Workstream D — Designer / Excel on-ramps

Where low-code and spreadsheet surfaces genuinely fit, without pretending actuaries will abandon
their tools.

### D1 · Lakeflow Designer as the "no-code data prep" on-ramp ◑
The prep stage (stage 1 — remapping, exclusions, large-loss adjustment) is the part a data-oriented
analyst wants to build visually rather than in SQL. Show **Lakeflow Designer** building the prep
flow that produces `demo_stage1_prepared_loss` — same governed output, visual authoring. This is the
"different front door to the same staged flow" point from the LDF doc, made real for the analyst who
doesn't write SQL.
*Real/gen2:* Designer generates the flow; output table is the same one stage 1 already writes.

### D2 · Excel as a first-class consumption surface ◑  *(the actuary's real habitat)*
Actuaries live in Excel. Two directions, both via the metric view / governed tables already built:
- **Read:** the `reserving_metrics` metric view is queryable live from Excel through the Databricks
  connector — triangles, factors, ultimates, all against one governed definition, no more "which
  extract is this?". (Mirrors the pricing/Excel accelerator pattern already in the estate.)
- **Write-back (optional, scoped):** an Excel template where an actuary types a selected pattern and
  it lands in `selected_development_pattern` as `PENDING_APPROVAL` — the same governed row the app,
  notebook and SQL all write. Proves the "any door, same governed record" thesis for the
  spreadsheet-first actuary. Reuses the delta-row-editor / write-back pattern from the estate.
*Real/gen2:* read is the metric view (exists); write-back is a thin add on the existing selection
write path.

### D3 · One-click "export the committee pack to Excel" ◔
The reserving committee still wants an Excel pack. A button that writes `demo_stage3_ultimate` +
selections + audit to a formatted `.xlsx` (openpyxl) — ultimates tab, selections/audit tab carrying
`applied_selection_id` + approver + rationale (the "your Excel now carries its provenance" line).
Already sketched in an earlier task list; belongs here.
*Real/gen2:* reads governed tables; writes to a volume with a download link.

Phases 1–2 are the ones that change what you can honestly say in the room. 3 is the differentiator.
4 is completeness.

## 7 · What we are deliberately NOT doing

- **Not replacing ResQ / building a reserving package.** No exotic curve libraries, no decades of
  edge cases. The seam stays; track-3 in B2 is "plug yours in if you own one."
- **Not faking the engine to look deeper than it is.** Every method that appears is a real
  registered model that runs; the honesty panel (B3) states the boundary out loud.
- **Not duplicating business data** for any new triangle — incurred, net, counts are all views.

---

## 8 · The one-sentence test for "done"

> *A reserving actuary with no reserving package sits down, builds paid and incurred triangles by
> segment, fits a tail, blends CL and BF by maturity, runs a bootstrap for the range, takes it gross
> and net, discounts it, overlays a judgement, signs it off, and reproduces it six months later —
> all governed, all versioned, all reproducible — and never opens Excel except to read the pack.*

Everything in this plan is in service of that sentence being true, and of the demo being able to say
so **without a working actuary catching it in an overclaim.**
